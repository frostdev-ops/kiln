# Kiln 0.2.0-dev.31.21

Fixes for mods' building tools (the brush picker, each brush's preview, tools that add terrain) and for a mod's spell or arrow list while you scroll. A ShroudForge mod that changes blocks now tells you why it does nothing in a game you joined.

## Players and server admins

- **Picking another brush keeps your tool.** With a mod's building tool (a `BuildingToolBlock`, for example a rubble tool), choosing another brush size in the picker turned the tool in your hand into the vanilla Overgrowth Tool. The brush you pick takes the tool's slot on the actionbar, as a vanilla Overgrowth shape does, and Kiln only recognised the tool itself there: from the first pick on, the picker listed the vanilla Overgrowth shapes and the next pick gave you the vanilla tool. The picker now keeps the tool's own brushes whichever of them is in the slot, also after you save and reload, in single player and on a dedicated server. If an earlier pick already left the vanilla Overgrowth Tool in that slot, put the mod's tool back there (craft it again if it is gone). Thanks to SonjaNemitz for the report and the traces (#153).
- **A brush's preview matches its size more closely.** Every brush showed the small vanilla shape's preview at the cursor, whatever its size. The game draws that preview as one fixed effect per vanilla size (0.5, 1.5 and 2.5 m), so a brush now shows the one nearest its radius: below 1 m the small one, below 2 m the medium one, from 2 m the big one. Kiln still gives the stroke the brush's exact radius (#153).
- **A building tool that adds terrain works from the second start.** A tool with an Add action needs a tool material pool, which is new to the game at the first start and kept for the next one. At that next start Kiln read the kept pool back as the wrong kind of pool and refused it ("unknown field entries"), at every start, so the tool and its brushes never came into the game and its recipe had no item ("output item ... not found"). The pool is now read back as a tool pool, also the one a 0.2.0-dev.31.14 to 31.20 game already kept, so such a tool works from the first start after the update. On a server, the server and every player's game each keep the pool for their own next start: a player who joins in their game's first start with the tool is refused at the join (the message names the pool) and gets in after starting the game once more. Thanks to SonjaNemitz, who found the exact line (#152).
- **Spell and arrow lists stay put while you scroll.** A mod that puts its own spells or arrows in place of the game's HUD list (Grimoire, for example) no longer flashes the game's own list for a moment after each switch, and on a dedicated server the cursor no longer jumps back to the equipped spell while you scroll on, so you no longer need to stop on each spell. Thanks to Fuzen777 for the report (#151).
- **A ShroudForge mod that changes blocks now tells you why it does nothing in a game you joined.** Only the server, or the player hosting, can change the world's blocks, in ShroudForge as with Kiln, so a mod such as Altar Cleanup has to run there. In a game you joined, it waited and gave up with nothing on screen, and kiln.log had only ShroudForge's own "original registered voxel grid contract is unavailable" or "voxel write was rejected before changing the world". Now Kiln shows one message over the game, "A ShroudForge mod tried to change blocks, but in a joined game only the server or host can. Run that mod there.", once per joined game however often the mod tries again. kiln.log gets one line that says the same and names the mod when its own log line shows which one. Thanks to netjunk for the report from a client joined to a dedicated server.
- In the same report, Altar Cleanup ran in netjunk's own hosted world: its "waiting: voxel grid: voxel-grid-pending" lines last for a moment while the world loads, then it scans, cleans up and undoes as it should. That is not a fault.

## Modders

- No mod API change: mod API 0.2.25, as in 0.2.0-dev.31.20. The MDK packs are 0.2.0-dev.31.21.
- **`Ui.AmmoList` in `Replace` keeps its rows on screen while the game builds the list again (#151).** When the game builds it again (a swap changed the backpack), the rows shown last and the cursor on them stay up until Kiln.Ui publishes the providers' rows for the new build, instead of the game's own rows and the game's selection. Picks of them are decided against the game's new rows (the backpack check of #145). The keep lasts at most 1 s, then the game's rows show until the next publication and kiln.log says so once; nothing is kept over another weapon, player, client session or world, or after the list is cleared. `Append` is unchanged. This is `Replace`'s default behaviour, with no API change, so Grimoire's 250 ms rest before a pick is no longer needed for this. Thanks Fuzen777.
- **Building tools (#152, #153).** kiln.worldtables: a replayed pool envelope is read back from its own section (`toolMaterialPools` when its canonical lists `entries`, `buildingMaterialPools` otherwise), the same way the envelope is read; define errors of a tool pool name it `toolMaterialPool`.
- kiln-tools brush picker: the frame is the held family's when its selected hotbar item is the root or any of its brushes (all 64, not only the 16 the picker lists) and the resolved item is that same item. The trace's `not selected` now means the slot holds neither; `not resolved` means the resolved item differs from the slot's.
- Each brush item now also sets `equipment.cursorVfx` to `item:Building_Overgrowth_Shape_Small`, `_Medium` or `_Big`, the vanilla shape nearest its radius. Its base stays `Building_Overgrowth_Shape_Small`. The ref is part of the brush's definition only: a mod's own content layer on its brush item's `equipment.cursorVfx` applies over it.
- The game's brush query has three other callers (`0xd180a0`, `0xd20190`, `0xd6aa05`). None of them is reachable on client 26430625, so they stay unadapted and no other brush list exists (`docs/re/building.md` 1.2.2, with the pick's path from the client to the host).
- `test-tool-content.sh` with extracted inputs takes two more files, `shape-medium.bin` and `shape-big.bin` (`extract_tool_content_inputs.py` writes them).
- **ShroudForge in a joined game.** ShroudForge's answers stay as ShroudForge has them: `runtime.world.voxel.get_grid_spec` answers `nil, "original registered voxel grid contract is unavailable"` (it never becomes ready there), and `runtime.world.voxel.write` is unavailable and answers `false, "voxel write was rejected before changing the world"` (outcome 1). Kiln adds only its kiln.log line and the toast. In `kiln/state/shroudforge.json`, `joinedWorldEdit` is `{session, mod, at}` for the last joined session it happened in (`mod` is `""` when no mod's line named it).
- The kiln.log reason of Kiln's voxel writer in a joined game is now "this game joined a server, and only the server or the player hosting can change the world's blocks; a ShroudForge mod that changes blocks has to run there (ShroudForge works the same way)"; with no world at all (the main menu) it is "no world runs in this game as its host yet".
- **World edits in multiplayer** ([shroudforge.md](../shroudforge.md#world-edits-in-multiplayer)): ShroudForge's own pattern, the same mod on both sides: the joined game sends with `runtime.network.send_mod` to `status().session_host_steam_id` (or `remote_dedicated_server_steam_id`), the server reads `receive_mod`, checks `runtime.network.player_permissions(peer_steam_id)` (`CanEditWorld`, ...) and writes.
- Under Kiln, ShroudForge's network transport is ShroudForge's own on both sides. On a Kiln dedicated server (a Linux lab server, Kiln 0.2.0-dev.31.19, with the probe below) ShroudForge's network service comes up with role `server` within about 4 s ("Network service is ready. Automatic Steam session acceptance and authenticated-peer health probes are active"), `status()` reports `available`, `service_ready` and the server's own Steam ID, and `send_mod`, `receive_mod`, `connected_peers` and `player_permissions` all answer (an unknown peer: "this player is not in this game or has not logged in yet"). In netjunk's game client joined to a dedicated server (31.19) it came up with role `client` too. A message from a joined game to a Kiln dedicated server has not been seen yet (it needs a real game client). For that check, Kiln's repository has `mods/tests/sf-net-probe` (`kiln-sf-net-probe`): install it on both, join, and read the `net-probe:` lines in both kiln.logs.
- Kiln mode (Kiln's interpreter for ShroudForge mods) has no voxel write yet, hosted or joined; in a joined game its `get_grid_spec` gives ShroudForge's same answer, without the message.
