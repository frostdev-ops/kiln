# kiln.creatures

What one creature or NPC is and does at runtime, server-authoritative: the creature catalog, per-creature values with
per-mod layers (level, faction, scale, resistances, speed, damage, XP, loot, AI feature switches, home), a private copy
of template settings for one creature (its own view range, aggro range, arsenal), variants (a base template plus
overrides) spawned by code or applied to natural spawns, AI state/target events, commands (attack, guard, stay,
move, heal), and a lab-only readiness switch. Players without Kiln see the results: every change goes into components
the game replicates itself. Evidence: [docs/re/creatures.md](../../re/creatures.md).

| Layer | File |
|---|---|
| C table | `native/core/abi/services/kiln_creatures.h` (`kiln.creatures` v1) |
| Native | `native/services/creatures/` → `kiln/services/kiln-creatures.dll` |
| Symbols | `sigdb/symbols/server.d/creatures.json` (features `creatures.slots`, `.ai`, `.table`, `.ready`, `.arsenals`, `.reflection`, `.commands`, `.rules`, `.attacks`, `.arsenal_writer`); the same file resolves on the client exe 26404966 (hosted worlds) and on the old server 1273043, so there is no `client.d` overlay |

reflection on, commands on`, then `ready: ... marks on, lab readiness switch off`).

## C# quick start

Reference `managed/services/Kiln.Creatures/Kiln.Creatures.csproj` with `Private="false" ExcludeAssets="runtime"`.

```csharp
using Kiln;

// catalog (any thread): every enemy-AI, wildlife, animal and villager template
CreatureTemplate vukah = Creatures.Template("Vukah")!;          // name, display name or GUID
var bosses = Creatures.Templates.Where(t => t.IsBoss).ToList();   // 54 on svn 1285601

// one creature (tick thread); setters are layers of the calling mod
CreatureRef c = Creatures.Of(entity);
c.Level = 20;                                    // health follows (enemy_scaling): 119 at 1, 417 at 10, 1031 at 20
c.Faction = Faction.PlayerAlly;                  // fights on the players' side
c.Scale = 1.4f;                                  // ScaleComponent + transform scale
c.Resistance[DamageKind.Fire] = 0.5f;            // DamageSusceptibility slot (1 = normal, 0 = immune)
c.SpeedFactor = 0.8f; c.DamageFactor = 1.3f; c.XpFactor = 2;
c.Loot.Slots = (2, 6); c.Loot.Labels = labelsGuid; c.Loot.Disabled = false;
c.Features.Disable(EnemyFeatures.FleeHome | EnemyFeatures.ReturnHome);
c.Ai.Set("combatCommitmentSetup.view.range", 30); // private Enemy01BehaviorState copy for this creature only
c.Ai.Set("Aggro.applyEnemyValue", false);        // other template components: "Component.path"
c.Arsenal = otherArsenal;                        // private EnemyArsenalReference copy (same skeleton family!)
CreatureInfo? i = c.Inspect();                   // state, target, guard, home, level, health, features, layers ...
c.Reset();                                       // drops everything this mod changed on it

// variants and spawning
using var v = CreatureVariants.Register(new CreatureVariant {
    Id = "frost_vukah", Base = "Enemy_Vukah_Melee", Level = 15, Scale = 1.3f,
    Resistances = { [DamageKind.Ice] = 0 }, Ai = { ["combatCommitmentSetup.view.range"] = "30" } });
EntityId e = await Creatures.Spawn("frost_vukah", pos);              // or a plain template name
CreatureVariants.AddSpawnRule(new CreatureSpawnRule("Enemy_Vukah_Melee", "frost_vukah", Chance: 0.2, NightOnly: true));

// behaviour
[Subscribe] void OnState(CreatureStateEvent e) { /* e.Entity, e.From -> e.To, e.Condition */ }
[Subscribe] void OnTarget(CreatureTargetEvent e) { /* e.Acquired / e.Lost, e.Target */ }
c.Command.Guard(player); c.Command.StopGuarding(player); c.Command.Attack(target, threat: 1000);
c.Command.Guard(player, new GuardOptions { CatchUpDistance = 40, Assist = false });   // or GuardOptions.EventOnly
foreach (var o in Creatures.GuardOrders) { /* o.Guard -> o.Target, o.CatchUps, o.Resent, o.ThreatsSent */ }
c.Command.Stay(); c.Command.MoveTo(pos); c.Command.Heal(seconds: 3);

// asks for Kiln's admin command /creature (see "Commands")
CreatureAdminCommands.Register();
```

## Ownership, revert and despawn

- Every setter writes a **layer of the calling mod** (its native owner). Several mods can change the same value: the
  last one on top wins, and when it lets go the next layer (or the value before the first change) comes back. Feature
  switches combine (union of the mods' masks); a release clears only the bits Kiln added, so feature bits the game's own
  arsenal actions toggled stay as the game left them.
- **Mod unload** (`Retiring`): the mod's layers and private copies are reverted, its variants and spawn rules removed,
  and creatures it spawned with `Creatures.Spawn` (`DespawnOnUnload`, default true) destroyed. Lab: unloading
  EliteVukah turned a level-20 elite back into a level-1 Vukah with the template's view range, 0 layers, 0 copies.
- **Data packs** own layers under a named owner (`"pack:<mod id>"`): `Creatures.RevertJson(owner)` reverts them.
- **`/creature`** changes are layers of its own named owner (`"kiln.creatures:command"`), not of a mod: `/creature
  reset` drops them on one creature, and they are reverted when the command goes away (see "Commands").
- **Despawn**: every Pre, each creature with state is checked by its engine record (the TemplateInfo pointer of its
  entity record); when it is gone (or its id now names another entity) its state is dropped without touching the world.
  Private copies are freed 250 steps (~10 s) after their slot stopped pointing at them.
- Setting a value on a gone creature throws `KeyNotFoundException`; a creature without the component (a villager has
  no `DynamicEnemy01BehaviorState`) throws `NotSupportedException`.

## Values (per entity)

| Member | Component (field) | Notes (lab, svn 1285601, player-free) |
|---|---|---|
| `Level` | `Level.dataStorage[0]` (clamped 1..`Level_Max`) + `DynamicEnemyScaling.nextUpdateTime = 0` | the game's `enemy_scaling` re-scales health (and damage) within a step: 119 → 417 at 10 (`NetworkLevel` follows), 1031 at 20, back to 119 on revert |
| `Faction` | `Faction.faction` (keen::FactionType) | PlayerAlly (11) = fights on the players' side |
| `Scale` | `ScaleComponent.uniformScale` + `CurrentTransform.scale` | both read back; how a client draws it: client checklist |
| `XpFactor` | `ExperienceSource.xpMod` | |
| `SpeedFactor` | `Movement` speed slots (sneak, walk, run, sprint, combat, custom, patrol, flee, swim/dive) × factor of the values before the first change | walk 2.4 → 1.2 at 0.5 |
| `DamageFactor` | `DamageMod_Multiplier`, `DamageMod` recomputed (base × multiplier + adder) | holds across `enemy_scaling` updates |
| `Resistance[kind]` | `DamageSusceptibility` slot (19: Physical, Cut, Pierce, Blunt, …, Fire 15, Fog, Ice, Lightning) | Physical/Cut/Pierce/Blunt are clamped 0..100 by the attribute; Magical is computed from its base/multiplier/adder |
| `Loot.Labels` / `.Slots` / `.Disabled` | `RandomLoot.defaultLabels`, `RandomLootSlotCount`, `RandomLoot.disableRandomLoot` | used when the game rolls the death loot (needs a player near: client checklist) |
| `Features.Enable/Disable` | `DynamicEnemy01BehaviorState.enabledFeatures` / `disabledFeatures` (EnemyFeature bits) | the template mask stays shared |
| `Home` / `Command.MoveTo` | `DynamicEnemy01BehaviorState.homeZonePosition` | roaming and return-home use it |

The C table has the same as `set(owner, entity, KILN_CF_*, index, value)` / `get` / `reset`; owner 0 writes without a
layer (nobody reverts it).

## Private template settings (`CreatureRef.Ai`)

The engine reads template components (`Enemy01BehaviorState` 2,520 B, `EnemyArsenalReference`, `Aggro`,
`EnemyScaling`, …) through an 8-byte per-entity slot in the entity's chunk (`GetTemplateComponent` → archetype
`+0x584 + 2·type`, captured in `creatures.json`). The first `Ai.Set` on a creature copies the component's current
template bytes, applies the field, and points that creature's slot at the copy; other creatures keep the shared data.

- Paths come from the game's own reflection at run time (`TypeByHash`, the same type records kiln.content reads), so
  nothing depends on offsets compiled into Kiln: `combatCommitmentSetup.view.range`, `combatSetup.cooldownGroups[0].cooldown`,
  `guardSetup.canGuardPlayer`, `fleeSetup.maxFleeDuration`, `enabledFeatures`; a path that names a component first goes
  to that component (`Aggro.applyEnemyValue`, `EnemyArsenalReference.arsenal`,
  `EnemyScaling.enemyLevelScaling.health`). Same tail as kiln.content's `templates` kind
  (`Enemy01BehaviorState.combatCommitmentSetup.view.range`), which edits the shared template for everyone.
- Values are text: numbers, `true/false`, enum names (`Melee`), flags (`UseTaunt|Move` sets, `+Sleep -FleeHome`
  changes), GUIDs, `keen::Time` in seconds (`4`, `250ms`). `Creatures.AiFields("Enemy01BehaviorState")` lists every
  field (path, type, offset, bytes).
- Lab (probe 4 as a test): `A reads a private copy (0x7E444FD0), B the shared template (0x61F633B8)`; `in 10 s
  enemy01's behaviour update for A read the copy 250x, the shared data 0x; other entities read the copy 0x`; it kept
  reading the copy `after 6 spawns, 2 destroys and a teleport` (chunk moves carry the slot).
- **Arsenal swap.** enemy01 looks the arsenal up by GUID every update (`ArsenalFind(registry, &guid)` in
  the per-entity function), so a private `EnemyArsenalReference` copy switches attacks live: the lab saw the new
  arsenal looked up for that creature only. Mixing works within one skeleton/animation-graph family
  (`CreatureTemplate.AnimationGraph` tells the family).
- Global template edits (kiln.content `templates`) do not reach a creature that reads a private copy of that component;
  Kiln.Creatures rebuilds copies from the template's current bytes (keeping the overrides) on `ContentReadyEvent`, and
  `Creatures.RefreshCopies()` does it on demand.
- Nothing of this is saved by the game: copies live as long as the entity (and the owner's layer).

**Sight and aggro: the fields the game reads.** The sight check of `enemy_combat_targets` reads
`combatCommitmentSetup`, not `aggroSetup`:

| Field | Does |
|---|---|
| `combatCommitmentSetup.view.range` | how far it sees a target (× `nightRangeFactor` at night, × `waterRangeFactor` in water, × `knownTargetsRangeFactor` for a target it already knows); Vukah 18, night factor 0.6 |
| `combatCommitmentSetup.view.coneHalfAngle` | the view cone (Vukah 90) |
| `combatCommitmentSetup.gain.inRange.range`, `.rangeWhileMoving` | within this distance a seen target is engaged at once; 0 = the creature's combat distances + 0.5 m |
| `aggroSetup.viewRange` | only the radius of the candidate query (`movement_sensor`, at least 64 m, set once when the creature first runs), so it matters only beyond 64 m |

No read of `aggroSetup.aggroRange` or `aggroSetup.viewConeHalfAngle` was found in the enemy programs of this build.

## Variants

A variant = a base template (a vanilla template or a kiln.content clone, by name/display name/GUID) + overrides
(level, faction, scale, xp, speed, damage, resistances, loot, features, AI paths).

- Base templates (and rule templates) resolve through kiln.spawn's list, else kiln.content's template data
  (`Content.Templates.Get`: clones are registered there first). A base neither knows yet is kept and resolved by a
  poll (~0.4 s); only names unknown to both are errors. Lab with CreatureTweaks: `pack creaturetweaks/...: 14
  change(s), 0 error(s)`, `spawn_replace (owner 0): chance 0.15`, `/creature spawn creaturetweaks_elite` ->
  `Kiln_Elite_Vukah ... level 20/105, health 1031/1031, scale 1.4`, viewRange 36 from the clone's template.
- `Creatures.Spawn(variantId | template, pos, yaw, options)` spawns the base through kiln.spawn **by name** (clones are
  found by name as soon as kiln.content registers them) and applies the overrides in the same tick, before the first
  sim step, so clients receive the creature with them. `CreatureSpawnOptions`: `Tag`, `Flags` (kiln.spawn's),
  `DespawnOnUnload` (default true).
- `CreatureVariants.Apply(entity, id)` applies a variant to an existing creature. `CreatureVariants.Of(entity)` names
  the variant a creature got this session. `CreatureVariantAppliedEvent` is posted after each application.
- **Natural spawns**: `CreatureVariants.AddSpawnRule(new CreatureSpawnRule(template, variant, chance, NightOnly,
  DayOnly))`. On kiln.gameplay's `NaturalSpawnEvent` (Post of the step that created the creature) a matching rule turns
  that very creature into the variant (same template, so the random spawner's bookkeeping is untouched). A rule whose
  variant has another base template (or a kiln.content clone) goes to kiln.gameplay's `spawn_replace` table: the
  random spawner spawns the variant's base instead (chance rolled there, on its worker thread) and Kiln.Creatures
  applies the overrides when the `NaturalSpawnEvent` arrives with `Replaced`. Day/night comes from Kiln.Time.
- Vanilla clients see a variant as its base template (name, look) with the changed level, health, faction, scale and
  behaviour. A variant of a kiln.content clone needs Kiln clients (`clients: "kiln"`, the clone's own rule).
- **Persistence.** Most creatures are DoNotSave (839 of 1,007 creature-like templates): nothing to persist. For saved
  templates (villagers, tamed animals) set `CreatureVariant.Persist`: the variant id is stored with Kiln.Saves'
  `EntityData` of the registering mod, and after a restart (entities re-matched by template + position) the variant is
  applied again (checked every ~2 s in that mod's tick). Plain layers (`Creatures.Of(e).Level = …`) are session-only;
  a mod that wants them across restarts stores them in its own `EntityData` and re-applies them.

### Data packs: the `creatures` section

kiln.content hands a pack's `"creatures"` section to `Creatures.ApplyJson(json, owner, source)` (registered with
`Content.RegisterSection` when Kiln.Creatures loads; sections that arrived earlier are replayed). Applying the same
owner/source again replaces what it added; `RevertJson(owner, source?)` removes it (owner-wide: its layers too).

```json
{ "creatures": {
    "variants": [ { "id": "elite_vukah", "base": "Enemy_Vukah_Melee", "name": "Elite Vukah", "level": 20, "scale": 1.4,
                    "faction": "Vukah", "xp": 2.5, "speed": 1.0, "damage": 1.3,
                    "resistances": { "Fire": 0.5 }, "loot": { "labels": "<guid>", "slots": [2, 6], "disabled": false },
                    "features": ["-FleeHome", "+Sleep"], "ai": { "combatCommitmentSetup.view.range": 30 }, "persist": false } ],
    "spawnRules": [ { "replace": "Enemy_Vukah_Melee", "with": "elite_vukah", "chance": 0.2, "night": true } ] } }
```
Errors (unknown base, missing id, unknown variant in a rule) and warnings (unknown keys) come back in the report.

## Behaviour

### Events (observe only, tick thread, Pre)

| Event | When | Fields |
|---|---|---|
| `CreatureStateEvent` | enemy01 `SetState` ran in the previous step | `Entity`, `From`, `To` (`EnemyState`), `Condition` (`StateCondition` from HandleCondition), `Step`, `Template` |
| `CreatureTargetEvent` | `SelectedTargets.targets[0]` of an active creature changed (checked every other step for creatures with a state change in the last 2 minutes) | `Entity`, `Target`, `Previous`, `Acquired`, `Lost`, `State` |
| `CreatureVariantAppliedEvent` | a variant was applied | `Entity`, `Variant`, `Natural` |

Mechanism: HandleCondition is the only caller of SetState (one call site); mid hooks at both entries (worker threads)
record (entity from the program context, old state from the dynamic state, new state, condition) in a buffer that Pre
drains. Nothing is recorded while nobody subscribes (one atomic load per call). Lab (forced readiness):
`Spawning->Idle (IsFinished), Idle->Roaming (IsReadyForRoaming), Roaming->Idle (IsFinished)`. Veto/redirect of state
changes is not in v1 (a decision would have to be taken on the worker thread from rule tables).

### Commands (`CreatureRef.Command`)

Sent as the game's own events by Kiln's SYSTEM program `kiln_creatures` with the game's emitter (the same path
kiln.gameplay's inject uses); their readers get them in the next sim step.

| Command | Game event → reader | Lab (player-free, forced readiness) |
|---|---|---|
| `Attack(target, threat)` | `AddThreatTargetEvent` → `enemy_threat_events` | `state Combat`, `CreatureTargetEvent 2542: 0->2543` (and B targeted A back) |
| `Guard(target[, GuardOptions])` | `StartGuardingEvent` → `enemy01` (its Guard state walks to the target), kept by Kiln (below) | `guardEntityId 2543 (B = 2543)`; follow, catch-up, defend, assist: below |
| `StopGuarding(target)` | `StopGuardingEvent` → `enemy01`; ends Kiln's order (its home goes back) | guard cleared |
| `Stay()` | StopGuarding + Kiln's order ends + `Home` = where it stands | |
| `MoveTo(pos)` | `Home` = pos (roaming/return-home walk it there; the enemy AI has no path command). It is not pathfinding: the game's own AI decides how it gets there, or whether. For a route, `Queries.FindPath` ([queries.md](queries.md#paths)) | home moved |
| `Heal(seconds)` | `RestoreEnemyHealthEvent` → `enemy01_pre_update` | a hurt, ready creature's health did not change in 6 s; use `Combat.Heal` |
| `ControlTarget(target)` | `RegisterControlledCombatTargetEvent` → `control_combat_target` | not observed |

Villager commands (`NpcCommandEvent {Reset, GoToPosition}` → `npc_active_behavior`) take an `NpcId`, not an entity id:
`Villagers` (`GoTo`, `Teleport`, `Stay`, `Follow`, `State`, `VillagerStateEvent`), table function `npc_command`. See [npcs.md](npcs.md).

### Guard orders (follow and defend)

The game's Guard state (20) is a path follow: every 0.5-2 s, when the guarded entity is `guardSetup.startDistance` (10 m
for the Vukah) or farther away, the AI enters Guard and asks the path walker for a path to it; when the walker answers
TargetNotReachable or Stuck it gives up after 0.5 s (Guard → Idle, IsFinished). That is the loop a real client
logged (the player stood where no path led) and what every lab run shows (no path grid without a player).
Evidence: [docs/re/creatures.md §12](../../re/creatures.md).

`Guard(target)` therefore sends the game's event **and** keeps an order (`Kiln.Creatures/Guarding.cs`, every ~0.4 s
in Pre), all through the game's own mechanisms:

| `GuardOptions` | Default | Does |
|---|---|---|
| `Keep` | true | the game dropped `guardEntityId` (an arsenal action, a death): the event is sent again (at most every 2 s) |
| `HomeFollows` | true | the guard's home zone moves with the target (a layer of the order's mod; restored at the end): idle roaming, the leash and "return home" centre on whom it guards |
| `CatchUpDistance` | 30 m | farther away: teleported 2.5 m from the target on its own side (kiln.world, `FindGround`); skipped while it fights unless twice as far |
| `StuckSeconds` | 4 s | stayed within 1.5 m of one spot that long while the target is beyond its guard range (the walker gave up): teleported the same way |
| `Focus` | true | enemy features Awareness and Investigate off while it guards (a layer of its own, given back at the end): the game's player companions (necromancy skeletons) have no Awareness, and an ally Vukah kept walking off to investigate noises |
| `Defend` / `Assist` / `Threat` | true / true / 2000 | whoever hurts the target, and what the target hits, gets `AddThreatTargetEvent` on the guard (kiln.combat's `EntityDamagedEvent`) |

`GuardOptions.EventOnly` is the old behaviour (only the event). The order ends with `StopGuarding`, `Stay`, a new
`Guard`, the guard's death or despawn, the target's despawn (StopGuardingEvent sent), or the owning mod's unload
(StopGuardingEvent sent). `Creatures.GuardOrders` lists them (catch-ups, resends, threats). Lab (creatures-test,
no player, forced readiness):
```
guard t+4.3s: A (3865.8, 833.0, 1463.8) B (3883.8, 833.0, 1463.8) dist 18.0 m, A Guard, home (3883.8, 833.0, 1463.8)
Kiln.Creatures: guard 2607 -> 2608: catch-up #1 (stood still 4.1 s, 18.0 m away (state Idle)): moved 2607 to (3881.3, 833.5, 1463.8)
guard t+5.1s: A (3881.3, 833.5, 1463.8) B (3883.8, 833.0, 1463.8) dist 2.5 m, A Idle
Kiln.Creatures: guard 2607 -> 2608: catch-up #2 (44.5 m away (catch-up distance 30)): moved 2607 to (3923.3, 833.5, 1463.8)
Kiln.Creatures: guard 2607: the game dropped the order (guard 0); sent again
Kiln.Creatures: guard 2607 (defends 2608): threat on 2609      -> PASS defend: ... A targets C
Kiln.Creatures: guard 2607 (assists 2608): threat on 2610
```
`StopGuarding` re-sends the game's StopGuardingEvent (after 1 s, up to 3 more times) until `guardEntityId` is clear:
one lab run in three still had it set 25 steps after the first event.

**In a client (a vanilla client joined a lab, LOCAL character):** an ally Vukah ordered to guard the player (`/creature watch`):
```

watch 8018: Guard at (3795.5, 839.9, 1459.7), target 0, guard 1 5.7 m from it, path walker Walking (PathFound)
```

was walking: fixed (the 1.5 m anchor). Not checked: defend/assist (enemies in the base are pacified;
lab-verified), how the teleport looks.
A companion recipe: a guard-capable body + `Faction = PlayerAlly` + `Guard(player)`.

### Readiness: what Kiln can and cannot do without a player

- A spawned enemy runs enemy01 every step (its behaviour update reads its template, its state machine evaluates
  conditions) but stays in **Spawning** until `Actor+0xBF8` bit 50 (IsReadyForGameplay) is set. The game sets it only
  where terrain is streamed, i.e. near a player (`actor_is_ready_for_gameplay`, captured as `creatures/actor.ready_bit`).
- **Lab switch**: with the file `kiln/data/kiln.creatures/force-ready`, `CreatureRef.ForceReady()` (C:
  `set_ready(owner, e, KILN_CREATURE_READY_FORCE)`) sets the bit every Pre. The AI then leaves Spawning on its own
  (Idle ↔ Roaming), takes guard orders and threat targets, enters Combat — but it does **not walk** (no path grid
  without a player) and attacks never land (no collision events). Without the file it returns `KILN_ERR_UNAVAILABLE`:
  forcing readiness on a production server would desync clients (the Actor state is replicated and the game marks it
  when it changes it).
- Without a player Kiln can verify: values, health scaling, private copies being read, arsenal lookups, state machine
  transitions, guard/threat bookkeeping, events. Movement, attacks, aggro at range, flee, loot rolls and how a client
  draws scale need a joined player (client checklist).

## Rules and arsenals

An arsenal holds a creature's attacks and rules, and the AI looks it up by GUID in every update. The game's rule walker already
does `{when, every, cooldown, conditions, actions}` on triggers. Kiln writes arsenals as data, and adds its own condition and
action kinds to the game's lists. The game keeps its combat states, blocking, flanking and hit reactions.

```csharp
using Kiln;

// A new arsenal. Its GUID follows from the mod and the name. Put it on a creature with c.Arsenal, or in a variant's AI values.
var thrower = Arsenals.Define("thrower", new ArsenalSpec
{
    From = Arsenals.OfTemplate("Enemy_Vukah_Melee"),    // the low-level way to start from a game arsenal; optional
    Attacks = [ new ArsenalAttack { Name = "long-throw", Sequence = throwStone, Style = ["Normal"], MaxRange = 40,
                                    Selection = [Is.TargetBetween(3, 40)] } ],
    Rules =
    [
        new ArsenalRule { Name = "rally", Every = 1, Cooldown = 20,
            If = [Is.Game("StateConstrain", ("states", new[] { "Combat" })), Is.HealthBelow(0.5)],
            Do = [Act.Custom(npc => Combat.Heal(npc.Entity, npc.HealthMax / 4))] },
        new ArsenalRule { Name = "night", Every = 2, If = [Is.Night, Is.Custom(npc => Weather.IsStorm)], Do = [Act.Attack("long-throw")] },
    ],
});
creature.Arsenal = thrower.Id;

// Or add to an arsenal the game has, for every creature using it. Its own attacks and rules keep their indexes.
Arsenals.Extend("Enemy_Vukah_Melee", new ArsenalSpec { Rules = [ /* ... */ ] });
```

### Threads

The dispatcher runs on the game's job threads, where the tick API faults. **Nothing a mod writes runs there, and the API has no way to
pass a delegate to that side:**

| You write | Runs on | What the job thread does |
|---|---|---|
| `Is.Custom(npc => ...)` | the tick thread, every `every` seconds, per creature using it | reads the published value. It is as old as its last check, and false until the first one |
| `Act.Custom(npc => ...)` | the tick thread, in the Pre after the rule fired, with the full API | queues it |
| `PickAttack`, `PickTarget` | the tick thread, every `PickEvery` seconds | reads the published override |

`npc` is an `NpcView`: `Entity`, `Creature`, `Health`, `HealthFraction`, `State`, `Target`, `TargetDistance`, `Position`, `InPhase(name)`.
A condition or action that throws is logged once and counts as false. Each table update happens in Pre, when no job runs, and swaps one pointer.

`[AdvancedApi]` `Is.Job`, `Act.Job` and `Arsenals.JobHandler` are the one exception, for a hot path you have measured: an
`[UnmanagedCallersOnly]` function on the job thread. KILN107 applies. Native plugins get the same through `rules_job_handler`.

### Conditions and actions

| `Is.` | Kind | Needs | Note |
|---|---|---|---|
| `HealthBelow(f)`, `HealthAbove(f)` | the game's `EnemyHealthPercentageConstrain` | no hook | fraction 0 to 1 |
| `TargetWithin(m)`, `TargetBeyond(m)`, `TargetBetween(a, b)` | the game's `DistanceConstrain` | no hook | |
| `Game("StateConstrain", ("states", ...))` | any of the game's | no hook | fields by the game's names; enums and flags by name, times in seconds |
| `HasBuff(guid)` | Kiln's | 2 hooks | re-read every 5 steps |
| `TimeBetween(from, to)`, `Night`, `Day` | Kiln's | 2 hooks | hours, wraps past midnight; re-read every 5 steps |
| `InPhase(name or guid)` | Kiln's | 2 hooks | any body: Kiln's phase, or the game's on a template with `EnemyPhases` (114 of 538) |
| `Custom(fn, every)`, `Named(name)` | Kiln's | 2 hooks | your code; `Arsenals.Condition(name, fn)` registers a name for data packs |

| `Act.` | Kind | Note |
|---|---|---|
| `Game("SetCombatStateAction", ...)` | any of the game's | no hook |
| `Custom(fn)`, `Named(name)` | Kiln's | your code, queued |
| `SetPhase(name or guid)` | Kiln's | any body. For a body's own phases and the `OnEnter`/`OnExit` rule modes that follow them, use the game's `SetPhaseAction` |
| `Attack(name or guid)` | Kiln's | starts that attack through the game's selection, past its style, range and constraints. It runs once the creature is in Combat, so say `StateConstrain` too |

Every condition has `.Not()`. A list means all of them; say any-of with `Is.Custom`.

Limits: 32 attacks and 32 rules per arsenal (the dynamic state's per-creature tables), 256 custom conditions per process. A rule's
`Chance` becomes the game's `RandomChanceConstrain`: its rule walker does not read `settings.chance`. `AttackDesscription`'s other
fields go in `ArsenalAttack.Fields` by the game's names. An attack's `Cooldown` constraint is `CooldownConstrain`, time since the creature's
last attack of any kind; a cooldown of its own takes a group from the template's `combatSetup.cooldownGroups`.

Change a base entry with `ModifyIndex` or `Modify` (its GUID) on an `ArsenalAttack` or `ArsenalRule`: fields you leave out stay, lists you give
replace. To take a base attack out of play, give it `Style = []`.

### Data packs

The same in the `creatures` section. Names follow from the pack's mod. Friendly conditions: `healthBelow`, `healthAbove`, `targetWithin`,
`targetBeyond`, `hasBuff`, `time`, `night`, `day`, `inPhase`, `custom`, `not`. Friendly actions: `setPhase`, `attack`, `custom`.
Anything else is passed to the writer as it is.

```json
{ "creatures": { "arsenals": [
    { "extends": "Enemy_Vukah_Melee",
      "rules": [ { "name": "rally", "every": 1, "cooldown": 20,
                   "when": [ { "type": "StateConstrain", "states": ["Combat"] }, { "healthBelow": 0.5 }, { "custom": "storm" } ],
                   "do": [ { "custom": "shout" } ] } ] },
    { "id": "thrower", "from": "Enemy_Vukah_Melee",
      "attacks": [ { "name": "long-throw", "sequence": "99a97b35-10e9-45aa-916a-5c53f7a20f5f", "style": ["Normal"], "maxRange": 40 } ] }

```

### Overrides

```csharp
c.Attacks.Force("slam");     // or an index: whenever it attacks, this one, past style, range, cooldown and constraints
c.Attacks.Allow(0, 3);       // the game picks with its own rules, among these
c.Attacks.Natural();         // the game's choice (an arsenal with PickAttack stops waiting)
c.Attacks.Clear();           // drops this mod's override

new ArsenalSpec { PickAttack = npc => npc.HealthFraction < 0.5 ? "slam" : null, PickTarget = npc => npc.Target, PickEvery = 0.25 };

c.PreferTarget(other, 5);    // holds this combat target for 5 s, then the game chooses again; c.ReleaseTarget() ends it. No hook
c.AiEnabled = false;         // the game's AI switch, a layer of this mod
```

**Every start path holds.** An attack becomes a creature's selected attack in `SetCurrentAttack`, from two places: `BeginAttack`, after a
selection, and the combo path inside AttackExecution, where a sequence's follow-up that names another attack starts it with no selection at
all. An override makes the game's own selection pick the forced attack, so its use counters, cooldown group and chosen target go to that attack;
refuses combo follow-ups; refuses a rule that plays a refused attack's sequence directly; and counts whatever reaches `SetCurrentAttack` against it
(`StartsOffOverride`, and it corrects a forced one). An attack already running when you set an override plays to its end. A forced attack still has to reach: it starts once the creature is within the attack's `MaxRange`.
`Force(index)` checks the index against the arsenal the creature reads now: `ArgumentOutOfRangeException` when it has no such
attack, `NotSupportedException` when the creature has no arsenal (a villager, wildlife); `/creature attack` answers with the reason.
If the creature's arsenal changes later and lacks the forced index, the game picks on its own.
With `PickAttack`, a creature's first selection answers "nothing available" until the tick has asked your code, so no natural attack slips through.

**AI off.** The body, sequences and damage keep running. Decisions stop, and so does target upkeep: `enemy_combat_targets` checks the same switch and
clears `SelectedTargets`, so a `Brain` needs its own perception. `NetworkEnemy.state` holds its last value for clients.

### What blocks build on

`BehaviourBlock` lowers to these. Everything an author names is a name; nothing needs `From`.

| Block | Lowers to |
|---|---|
| `AttackBlock` | `ArsenalAttack` with `Name`; `Plays` to the sequence GUID; range to `MaxRange` plus `Is.TargetWithin` in `Selection` |
| `RuleBlock { Every, When, Do }` | `ArsenalRule { Every, If, Do }`; `Is` and `Act` are this file's |
| `Behaviour` of a creature | `Arsenals.Define(<block name>, spec)`, then the arsenal's GUID as `EnemyArsenalReference.arsenal` in the template or variant |
| `PickAttack`, `PickTarget` | `ArsenalSpec.PickAttack`, `PickTarget`; per creature `c.Attacks`, `c.PreferTarget` |
| `Brain` | `c.AiEnabled = false`, then `ActorInput` and sequences on the tick; say that perception stops with it |
| JSON | the `arsenals` list above, or the JSON `RuleCondition.ToJson()` shows |

Call `Define` and `Extend` from mod code: additions belong to the calling mod and go when it unloads. A mod has one set of additions per arsenal: calling again for the same arsenal replaces them, and other mods' stay. A type or field the game's reflection does not have throws
`ArgumentException` at once with the reason, so a block can pass it on. What depends on the base (the limits) shows in `Arsenals.Info(id).Problems` from the next step: that owner's additions are left out, and the others stay. A `From` that does not exist yet is logged, and the arsenal appears once it does.
`Arsenals.Info` lists attacks by index, GUID and sequence. A sequence is not checked against the body's graph: a state the graph lacks does not fail, the creature holds its pose while the
sequence's impacts run, so the state agreement in a block's `Define` is what catches it.

The writer: `arsenal_define` takes `{ "guid", "from"?, "attacks": [...], "rules": [...] }`. Attack keys are `guid`, `sequence`, `modify` or `index`, `selection`, `execution`, `abort`, `commands`, `data`, and any
field of `AttackDesscription`. Rule keys are `guid`, `mode`, `every`, `cooldown`, `chance`, `modify` or `index`, `when`, `abort`, `do`. An entry of a list is `{ "type": "DistanceConstrain", "min": 0, "max": 3 }`, the form `tools/kfc` prints (`$type`, `value`) too, or
one of Kiln's: `{ "kiln": "condition", "slot": n }`, `"buff"`, `"time"`, `"phase"`, `"job"`; `{ "kiln": "queue", "id": n }`, `"phase"`, `"attack"`, `"job"`. See `kiln_creatures.h`.

### How it works, and what it costs

- **The writer** builds a self-relative record in Kiln's memory and points the registry's GUID map at it, in Pre. A GUID the game knows becomes a composite: the game's arsenal, then each owner's additions in
  order. The game's blob is not touched. Removing an owner rebuilds; the last one puts the game's pointer back, or takes the map entry out. A creature can still hold the index of a rule that went away, so a hook on the
  behaviour update resets it, once an arsenal has shrunk. After a `kiln.content` change the composites are rebuilt (`ContentReadyEvent`, `Arsenals.Refresh()`).
- **The record layout** (offsets of attacks and rules inside an arsenal) comes from the reflection when the service is ready. Overrides need it: without it the hooks are not installed and `Force` throws `NotSupportedException`.
- **Hooks go in at first use and come out when nothing uses them:** `ConstraintEval` and `ActionExec` for Kiln's kinds; `SelectAttack`, `AttackAvailable`, the follow-up lookup and a mid hook on `SetCurrentAttack` for overrides. Data-only
  arsenals need none. A server without rule mods runs none of this.
- **Fails soft.** A target that does not resolve: `Arsenals.RulesState` (an `ArsenalRulesStatus`) says so (the older `Arsenals.Status` / `RulesStatus` are obsolete: Kiln.Rules has a `RulesStatus` of its own, so a mod using both could not name it), and what needs it throws `NotSupportedException` with the reason. Without the dispatcher, data-only arsenals still work; without the registry map, no arsenal can be written; without the attack targets, overrides are off. The AI switch needs none of them. Creatures run on either way (lab, with each target's pattern broken in turn). With no hooks loaded Kiln's kinds in a record are harmless: the game reads them as false and no-op.

**Cost, lab, 100 Vukahs fighting in pairs, each with 3 rules on Kiln's kinds and an allow mask** (4 runs of 400 steps):

| Part | Per step |
|---|---|
| Tick side, native (the table for 100 creatures) | 3.7 to 6.9 µs |
| Job side, Kiln's kinds | 1.1 to 1.4 µs: 12 to 20 kinds at 67 to 95 ns each |
| Tick side, managed (conditions, actions) | 30 to 67 µs, the test's own lambdas and `NpcView` reads included |
| The whole sim step, no hooks / all of this on / hooks out again | 5.06 / 5.67 / 6.42, 8.20 / 6.94 / 8.18, 5.19 / 4.29 / 4.13, 10.20 / 11.36 / 13.58 ms |

So the step's own time shows no difference above run-to-run noise, which is 1 ms or more on a busy machine. Forwarding the game's own constraints and actions through the hooks was not timed apart from that. `kiln.log` gives each install as 0 ms, on a millisecond clock; removal was not timed.

`/creature rules [entity]` shows all this; `/creature attack`, `aiswitch`, `target` drive it.

## Commands (`/creature`, admins)

`/creature` belongs to Kiln (owner `kiln`, permission node `kiln.command.creature`, level Admin). A mod that wants it
calls `CreatureAdminCommands.Register()` (EliteVukah and RuleVukah do): the first call adds the command, later calls
share it, and it stays while one of those registrations is held. It goes when the last one is disposed or its mod
unloads. What the commands change (values, AI overrides, attack overrides, the AI switch, held targets, guard orders)
belongs to the command's own owner `kiln.creatures:command`, so another mod's unload never reverts it. `/creature reset`
drops it on one creature; when `/creature` goes away, all of it is reverted.

## Replication marks

Kiln writes creature components on the tick thread. The engine replicates and saves changes it was told about
(`MarkWritten` inside a program), so a raw write of a rarely changing component (Faction, ScaleComponent) would reach
clients only by luck. Kiln's raw-mode program `kiln_creatures_marks` (write access to Faction, ScaleComponent,
CurrentTransform, Level, ExperienceSource, RandomLoot, RandomLootSlotCount, DamageSusceptibility, DamageMod, Movement,
DynamicEnemy01BehaviorState) marks exactly the components Kiln changed, in the step after the change, and returns at
once (without iterating) in steps with nothing to mark. Lab: `marks: 1 entity(ies) to mark, 2 iterated, 0 not found, 11
component(s) marked`. That the client then shows the change is on the client checklist.

## Cost

Idle (no subscribers, no changes): two mid hooks that load one atomic, one Pre callback that walks the (empty) state
map, and the marks program returning at once. With state-event subscribers: a thread-local store per HandleCondition
and a locked push per SetState (a few per second per active creature). Each creature with state costs one entity-record
lookup per Pre (despawn check) plus one slot lookup per private copy.

## The contract (dev.27)

Kiln.Creatures follows [the API contract](../modding/contract.md). Server side only (`[ServerOnly]` on `Creatures`, `Arsenals`, `Villagers`,
`CreatureVariants`).

- **Capabilities.** `kiln.creatures` and its sigdb features (`creatures.ai`, `arsenal_writer`, `arsenals`, `attacks`,
  `commands`, `ready`, `reflection`, `rules`, `slots`, `table`), lowered by Kiln.Creatures when the service is not
  loaded.
- **Errors.** Without the service every call throws `KilnUnavailableException` naming `kiln.creatures` (a
  `NotSupportedException`, as before); so do `Arsenals` and the NPC commands on an older kiln.creatures. An arsenal
  the build cannot define names `creatures.arsenals`, an attack override it cannot install `creatures.attacks`.
  **Not changed:** a per-creature call the native side answers "unavailable" keeps throwing a plain
  `NotSupportedException` ("the entity lacks that component, or this build/world does not support it"): that is as
  often a refusal about one creature as a missing capability, so it names none. A result shape for the
  `CreatureRef` setters is not in this release.
- **Events.** `CreatureChangedEvent` (new) is posted for every change a mod makes on a creature: a `CreatureRef`
  value (`Level`, `Faction`, `Scale`, `Home`, resistances, loot, features), `AiEnabled`, `Phase`, the held target, an
  AI override (`Ai.<Component>.<path>`), `Reset` and `Ai.Reset` (these two only when something was dropped or the AI
  came back on: nothing for a creature that is gone or one the mod had not changed; `Reset` also counts what the mod
  held: a target, an attack override, a readiness hold, its AI switch). A write made by a handler while
  the event is being dispatched is posted at the start of the next step, once per value, and only if that creature is
  still there (not when its id names another entity by then): such a handler cannot loop
  ([contract](../modding/contract.md#3-change-events)). The game's own changes keep `CreatureStateEvent` and
  `CreatureTargetEvent`. Commands (`Command.Attack`, `Guard`, ...) and `AttackControl` raise nothing of their own:
  the game answers them with state and target changes.
- **Threads.** `[TickThreadOnly]` on everything that touches a creature; `Creatures.Status` and `Available` are
  `[AnyThread]`.
- Tested offline: rows, exceptions, attributes, the service's start (`ServiceStartTests`), and the writes with
  subscribers on a fake kiln.creatures table (`ChangeEventTests`). Against a real kiln.creatures no lab run in dev.27
  has watched the event.
